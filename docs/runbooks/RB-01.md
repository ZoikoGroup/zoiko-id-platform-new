# RB-01: Authorization decision degraded (PDP latency or error burn)

**Services:** authorization · **Tier:** T0 · **Owner:** @zoiko/authorization

## Trigger

`authorization-availability` or `authorization-latency` burn-rate PAGE; AuthZEN p95 above 60 ms in-region; synthetic ALLOW/DENY probe failing.

## Impact

Protected actions cannot be authorized. The PEP fails closed (DENY), so customers see refused actions; no unsafe ALLOW is possible from a degraded PDP.

## Preconditions

Operator Console access at AAL-Z3. Read-only diagnosis needs no JIT grant; any configuration change follows the normal release path.

## Diagnosis

1. Open dashboard `zid-authorization`: split latency by risk class and reason code; check whether DENY rates rose with latency.
2. Check policy runtime: active policy release revision, bundle load errors, relationship projection lag (`zid_projection_lag_seconds`).
3. Check the database: connection pool saturation (RB-06), replica lag on read paths (RB-05).
4. Check the last deploy and feature-flag changes for the service (`release.deployed` events).

## Mitigation

1. If a release correlates: roll back to the previous digest (RB-18).
2. If projection lag: pause bulk relationship writers; let the projector catch up. Never serve decisions from a projection older than the R2/R3 freshness bound.
3. Shed T2/T3 load (administration, batch) before touching T0 capacity.

## Recovery

1. Scale PDP replicas within the approved capacity envelope.
2. Re-enable shed work in reverse tier order once burn rate is below 1.0.

## Validation

1. Synthetic known-ALLOW and known-DENY fixtures pass in every cell.
2. p95 below 60 ms for 30 minutes; error budget burn below 1.0 in the 1h window.

## Rollback

Re-apply the previous replica count and re-enable paused writers; a policy-release rollback is itself a governed release (`policy.release.*`).

## Escalation

SEV1 if any tenant cohort cannot authorize for more than 5 minutes; Security Lead if DENY reason codes indicate integrity (`RELATIONSHIP_REVISION_UNPROVABLE`).

## Evidence

Incident timeline entries for every mitigation; DecisionReceipts are unaffected and must keep flowing (check `zid_evidence_receipts_total`).
